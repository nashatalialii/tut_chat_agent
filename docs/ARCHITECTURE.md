# Legal RAG Architecture

## Request path

```text
User question
  -> deterministic Arabic/Egyptian query processing
  -> semantic retrieval (BGE-M3 + Chroma)
     + lexical retrieval (local BM25 index)
  -> Reciprocal Rank Fusion
  -> legal reranker
  -> evidence validator
  -> grounded Ollama generation
  -> backend-built citations
```

Conversation memory is used only to resolve short follow-up references. Retrieved legal evidence has higher authority than memory.

## Why Chroma was kept

The existing Chroma integration already provides the semantic-search capability needed by the project. Hybrid retrieval was added by maintaining a derived BM25 index over the same canonical chunks. No vector-database migration is justified at this stage.

## Source trust

Legal source metadata supports `official`, `verified`, `unverified`, and `sample`. With `REQUIRE_VERIFIED_LEGAL_SOURCES=true` (default), generation is allowed only from `official` or `verified` evidence. The bundled demo document is marked `sample` and therefore cannot silently act as authoritative law.

## Versioning

Chunks preserve `version`, `effectiveFrom`, `effectiveTo`, and `isCurrent` when supplied by source metadata. Current versions receive priority unless the user explicitly asks for a historical/previous version. Unknown version dates remain unknown rather than being invented.

## Prompt-injection boundary

Retrieved text is passed to the LLM inside evidence delimiters and the system prompt explicitly defines it as untrusted data, never as application instructions. Citations are not generated by the LLM; they are constructed from retrieval metadata.

## Knowledge-base changes and cache

The ingestion pipeline writes a deterministic knowledge-base manifest/version. Redis answer-cache namespaces include knowledge-base version, legal version, model version, and conversation fingerprint. Re-indexing therefore stops old legal answers from matching new cache keys without deleting Redis globally.
